# JR knowledge and private work learning

## Inspected local pipeline

This document describes the `feat/jr-brain` implementation and its original local inspection. The server integration was subsequently published with explicit authorization on 2026-11-06; see [integration review](jr-review.md) for the current deployment and remaining checks.

Before this change, `TeachCardHost` mounted `useBrainCapture`: successful turns loaded new conversation stretches, forwarded them over IPC, redacted vault secrets, and persisted them in `jr-brain/queue.json`. Login resumed that queue. The control server authenticated the JR session and forwarded it to `/capture`; the brain returned `202 accepted` before the in-memory curator completed. The curator could be disabled, fail its model call, reject JSON, exhaust its budget, or drop a full queue while the desktop had already treated delivery as successful. Accepted candidates were immediately persisted as searchable facts. `brain_search` returned FTS5 hits filtered by JR areas, risk, active state and supersession; those hits reached the agent through the `jr-teach` MCP tool.

The new consent flow must use only a user-authorized excerpt, create a private draft, bind sharing to its exact version/hash, and require a verified ERP authorization context before publication, review or shared retrieval. Official drafts remain outside search until approved. Existing passive queue files and historical facts must not be deleted or replayed by this change.

## ERP authorization implemented

ERP PR #148 at `3605b469ff4a6c508542561ea67bae5394e1d172` defines authenticated `/mcp/vinculo` and the `erp.quem_sou` MCP tool. The former identifies the token's `app_users.id` and organizations; the latter returns direct organization memberships and module permissions. It does not define JR areas, area-to-module mappings or official-procedure approvers. The JR checkout now implements delegated OAuth with PKCE, encrypted server-side grants, verified ERP account linking and MCP calls under current ERP permissions. Configuration and review steps are in [JR control](jr-control.md).

The companion ERP implementation, tracked in [PR #148](https://github.com/lucaszocaratto15/erp-stratacerta/pull/148), adds the canonical `conhecimento` and `conhecimento-procedimentos` modules and the `conhecimento.autorizacao` MCP tool. The current policy supplies stable organization/module audiences and explicit read, publish, revise, withdraw and official-approval capabilities. Existing ERP knowledge tools enforce the same permissions. No function preset or employee grant is added automatically.

Do not infer identity or permissions from names, email, JR roles or renderer headers. MCP uses the canonical ERP group membership resolver and the primary company’s module permissions for every company in that group. Company remains a data-origin filter, not a separate JR access grant. Brain search uses the existing shared SQLite database as one group knowledge base: one FTS query, global ranking and limits, company origin preserved. The control service resolves the current ERP policy and signs a request-bound v3 context for group policy (v2 for a single company). Production Brain uses that policy without intersecting local JR memberships. Selected-company context still owns private drafts and edits. Search filters the ERP group IDs and stable module audience keys in SQL, along with provenance, consent, status and validity, before materializing candidates or applying ranking limits. Feedback follows the authorized fact’s real origin. Legacy facts remain quarantined. Relinking cannot reinterpret an earlier draft; the control service revalidates the session, connection, organization and policy before releasing the result. Missing policy or unavailable ERP still fails closed.

Revisions linked to an existing note retain its audience. An independently pasted manual excerpt has no verifiable external source policy; explicit sharing of that text must not be described as automatic inheritance of an external document's permissions. OAuth configuration and an existing-account login were subsequently verified in production; restricted-employee OAuth remains pending.

## Independent work-learning flow

Activity metadata and private routine records stay separate from shared knowledge. Observation requires a separate opt-in; pausing stops collection. New sources require renewed explicit consent even if an older version was enabled. Trusted main-process receipts now record five known successful ERP query tools and completed browser downloads. The operation captures employee and consent generation before starting; pause, revocation or logout invalidate pending receipts. Downloads honor exclusions using transient origin information that is never persisted. Failed, pending-consent and malformed ERP results are not completion evidence.

Only source categories and timestamps enter encrypted, employee-specific work events: no query, arguments, result content, document ID, filename, path or URL. App/window metadata remains weak evidence. Automatic event sequences are private routine candidates, never confirmed business facts. Manual milestones remain supported, and only reviewed routines enter a monthly map or a user-requested private manual draft. No draft is automatically published into the Brain. Existing raw work samples keep their original 48-hour purge/wipe policy; old Brain queues remain untouched.

## Local validation

Use temporary databases/directories and injected providers. Cover lack of consent, exact-version sharing, rejected/pending procedures, supersession, missing ERP authority, cross-organization access, private workflow records, pause, metadata sanitization and absence of sensitive diagnostics. Existing real queues and user records are outside the tests.

Implemented locally: explicit excerpt/revision/sharing UI; draft and official-review lifecycle; immutable supersession and validity filters; metadata-only diagnostics; legacy queue quarantine; current ERP policy and organization isolation; private-learning consent, immediate pause, encrypted observations, trusted real-event receipts, manual milestones, confirmed-only monthly maps and private manual drafts. Local lessons remain separate. One canonical JR assistant is bound to each authenticated employee; historical assistants without proven ownership remain preserved without automatic assignment. Legacy `/peers` and JR-area grants no longer expose other roles' handbooks. This increment does not observe arbitrary external application contents or prove completion of business writes.

Validation uses Vitest, Node JR tests, TypeScript, i18n generation/validation, lint, formatting and whitespace checks. Control-to-Brain tests use isolated OAuth/ERP providers and temporary SQLite databases. Companion ERP tests exercise its policy, MCP SDK and temporary PostgreSQL database, including migration replay, revocation, author-only changes, audience isolation and history.

An existing-account OAuth login and read-only group report were verified in production. Restricted-employee OAuth, all catalog outputs, external model response quality, packaged Windows/CRTI behavior and translated layout remain unverified. See [review instructions](jr-review.md). Private production evidence and historical patches live in the ERP repository, outside this public repository.
